# MOSS/Anima プロンプトビルダー 仕様書 v1.1

## 変更履歴

- v1.1（2026-10-30）
  - ネガティブの「全体ベース」の中身を定義（6章）
  - 服装の moss は完全な文で書く方式に変更し、none／空のときの文章処理を定義（4.2章、5章、7章）
  - `extraMoss` / `extraAnima` を廃止（差し込み位置が曖昧なため。例外はSituationのバリエーションを別ファイルで登録して対応する）
  - SceneとSituationの判定規則を明記（9.1章）
  - 空白の整形と重複タグの規則を明記（5章、7章）。なおAnimaポジティブの重複タグは**除去しない**
    （複数キャラの場面で `huge breasts` 等をキャラごとに繰り返し、各キャラへ行き渡らせるため）
  - UIの章を追加（10章）。選択方法はプルダウンではなく階層ツリー／ファイル選択とし、
    スロット枠はSituation読み込み時に動的に生成する
  - Sceneに `name`（表示名）を追加。MOSS JSONの出力形式、YAML書き戻しライブラリ、`outfits` の未指定の定義を明記
- v1（2026-10-30）初版

## 1. 目的

過去に作成した画像生成プロンプトについて、**キャラクターだけを入れ替えて再利用**できるようにする
プロンプトビルダー兼データベースエディタ。

- 例：射命丸文のシーンを犬走椛に差し替える／ポケモン三人組のシーンを別の三人組に差し替える
- アプリ上でキャラを変更すると、**MOSS用プロンプトとAnima用プロンプトの両方**が自動で再生成される
- データベースは人間が読めて手で編集できること（YAMLファイル群）

## 2. スコープ

### やること（v1）

- シチュエーションは**固定テンプレート**とする（場所・背景・動作・状態・表情まで全部テンプレート側に書く）
- 差し替え可能なのは **キャラクター** と **服装** のみ
- テキスト断片は「MOSS用文章」と「Anima用タグ」をそれぞれ1つのブロック（文字列）として保持する
- 画面は「シーン組み立て画面」1つだけ（10章）。マスターデータの編集はエディタで直接YAMLを編集する運用とする

### やらないこと（v1では実装しない。ただしデータ構造には将来の余地を残す）

- プレイ（行為）だけを分離して差し替える機能 ※プレイはシチュエーション内に固定で書く
- キャラの部位・項目単位でMOSS文章とAnimaタグを対応付ける変換
- キャラの「形態」を1レコード内の分類として扱うこと ※形態違いは**別キャラクターとして登録**する
- シーン単位の自由文の差し込み（旧 `extraMoss` / `extraAnima`。v1.1で廃止）

## 3. 用語とエンティティ

| エンティティ | 意味 |
|---|---|
| Character | キャラクターのマスターデータ。1キャラ（1形態）につき1ファイル |
| Outfit | 服装データ。1服装につき1ファイル。キャラとは独立 |
| Situation | 固定テンプレート。スロット（差し込み口）とプレイスホルダーを含む |
| Scene | 生成単位。Situation＋キャスト割当を確定させたもの。コンパイル結果を保持する |
| Cast | Scene内でスロットに割り当てられたキャラ。Sceneの `cast` がその実体であり、独立ファイルは持たない |

## 4. データモデル

### 4.1 Character

```yaml
id: elesa_bw            # 必須。一意。[a-z0-9_] のみ。ファイル名と一致させる
name: カミツレ（BW版）   # 必須。日本語の表示名
group: elesa            # 任意。同一人物の形態違いなどをUIでまとめるための緩い分類
tags: [ポケモン, BW]     # 任意。検索用キーワード
defaultOutfit: elesa_bw_summer  # 任意。Outfitのid
moss: |                 # 必須。MOSS用の容姿文章（ブロック）
  （文章）
anima: |                # 必須。Anima用のタグ文字列（ブロック）
  （タグ）
negativeMoss: |         # 任意。このキャラ固有のネガティブ（MOSS用）
negativeAnima: |        # 任意。このキャラ固有のネガティブ（Anima用）
```

記載ルール：

- **頭部アクセサリーはキャラ側に含める**（例：カミツレのヘッドホンは moss/anima 両ブロックに書く）
- 頭部以外のアクセサリーは服装側に含める
- Animaのキャラ名タグによって自動で発生してしまうアクセサリー等は**許容する**（排除のために戦わない）
- 陰毛の色・濃さはキャラの情報として、ブロック内に文章／タグとして含める。色の既定は髪色に合わせる
- キャラ固有ネガティブの主な用途は「別バリアントの排除」（違う髪型・違う色など）と「身体特徴の保護」（肌色など）

### 4.2 Outfit

```yaml
id: guilty_pink         # 必須。一意。ファイル名と一致
name: ギルティ衣装（ピンク） # 必須。表示名
tags: []                # 任意
moss: |                 # 必須。服装の完全な文（下記の記載ルール）
anima: |                # 必須。服装のタグ
negativeMoss: |         # 任意。服装固有のネガティブ
negativeAnima: |        # 任意
```

記載ルール：

- **moss は「She wears 〜.」まで含めた完全な文で書く**（主語は着用者に合わせたものを著者が書く）。
  Situation側は `{{slot.outfit}}` プレイスホルダーだけを置き、文の形は服装側が持つ。
  これにより、服装が `none`／空でも壊れた文が残らない（5章）
- 色違いの排除ネガティブ（例：ピンク枠なら他色のスーツを排除）は、キャラではなく**服装側**に持つ

### 4.3 Situation

```yaml
id: beach_chat          # 必須。一意。ファイル名と一致
name: 海辺で談笑          # 必須。表示名
tags: [海辺, 日常]       # 任意
rating: safe            # 必須。safe | sensitive | explicit
slots: [left, center, right]  # 必須。スロット名の宣言（1つ以上、一意）
canvas: { w: 1536, h: 1024 }  # 必須。生成サイズ
outfits:                # 任意。スロットごとの服装指定（Outfitのid、または文字列 none、または未指定）
  left: guilty_pink
mossPrompt: |           # 必須。MOSSレイアウトJSON文字列（プレイスホルダー入り）
animaPrompt: |          # 必須。Animaタグ文字列（プレイスホルダー入り）
negativeMoss: |         # 任意。シチュエーション固有のネガティブ
negativeAnima: |        # 任意
```

### 4.4 Scene

```yaml
id: beach_chat__trio    # 必須。一意
name: 海辺で談笑（ポケモントリオ）  # 任意。表示名
situation: beach_chat   # 必須。Situationのid
cast:                   # 必須。スロット名 → Characterのid
  left: skyla_bw
  center: elesa_bw
  right: hex_maniac_xy
outfits:                # 任意。スロットごとの服装上書き（Outfitのid、または文字列 none、または未指定）
applyNegative: false    # 任意。既定 false（6章）
compiled:               # コンパイル／生成時にアプリが書き込む
  mossPrompt: （最終文字列）
  animaPrompt: （最終文字列）
  negativeApplied: false  # その生成でネガティブを適用したか
  seed: null
  images: []              # 生成画像のパス
```

置き場：Situationと同じフォルダに、ファイル名 `<situation id>__<scene名>.yaml` として置く。

### 4.5 フォルダメタ `_folder.yaml`

フォルダ内に任意で1つ置ける。なくても動作する。

```yaml
name: 海辺               # 任意。フォルダの日本語表示名
description: （任意）     # フォルダの説明
order:                  # 任意。子要素の並び順（ファイル名／フォルダ名のリスト）
  - beach_chat.yaml
```

## 5. プレイスホルダー仕様

- 書式は2種のみ：
  - `{{スロット名}}` … そのスロットのキャラクター
  - `{{スロット名.outfit}}` … そのスロットに解決された服装
- **MOSS/Animaの区別はプレイスホルダーに書かない**。`mossPrompt` 内ではMOSSブロックに、
  `animaPrompt` 内ではAnimaブロックに自動で解決される
- 同一プレイスホルダーの複数回出現を許可する（summaryとitemの両方に同じキャラを書くため）
- **空白の整形**：YAMLの `|` ブロックは末尾に改行が付くため、各ブロックは
  **前後の空白（改行含む）を除去してから差し込む**。MOSS・Animaの両方に適用する。
  差し込み後の文章についても、連続する空白は1つに整える
- **空の服装の扱い**：服装が `none`／未解決で空になった場合、`{{slot.outfit}}` は空文字列に置換される。
  - MOSS側：服装の文そのものが服装ブロック側にあるため、空でも文は壊れない
  - Anima側：置換後に生じる**空タグと連続カンマを除去する**（カンマで分割し、空白のみの要素を捨てて再結合する）
- バリデーション：
  - 宣言されていないスロット名の使用 → エラー
  - `cast` で割り当てられていないスロットが残る → エラー
  - 宣言されたが未使用のスロット → 警告

### 服装の解決規則（優先順位）

服装はCharacterとSituationの両方が持ちうる。両者は無関係であり、コンパイル時に次で解決する：

1. Scene の `outfits` で指定があればそれ
2. なければ Situation の `outfits` で指定があればそれ
3. なければ Character の `defaultOutfit`
4. いずれもなければ服装テキストなし

服装指定は三値とする：**Outfitのid ／ `none`（文字列。明示的に着せない）／ 未指定（下位に委譲）**。

- 「未指定」とみなすのは、**キーがない場合と、値が null の場合の両方**とする
- 「未指定」と「none」を区別すること。区別しないと、服装に言及しないシチュエーションで
  キャラの服が意図せず付く事故が起きる

## 6. ネガティブプロンプト

- ネガティブは Character / Outfit / Situation がそれぞれ保持する（MOSS用・Anima用を別文字列で）
- 最終ネガティブは **層の連結** で合成する（優先で1つ選ぶのではない）：
  `全体ベース ＋ 登場キャラ全員のネガ ＋ 解決された服装のネガ ＋ Situationのネガ`
- **全体ベース（アプリ側の定数）は次に固定する**：
  - MOSS用：`photorealistic, realistic, blurry, low quality, worst quality, text, watermark, deformed hands, extra fingers, extra limbs, censored, mosaic`
  - Anima用：`worst quality, low quality, score_1, score_2, score_3, artist name, blurry, jpeg artifacts, chromatic aberration, censored, mosaic censoring`
- **重複除去の規則**：カンマで分割し、各要素の前後の空白を除いたうえで、
  **大文字小文字を区別せずに**比較し、最初に出現したものを残す
- **適用はオプションとし、既定はOFF**（`Scene.applyNegative`、既定 `false`）。
  思わぬ影響（例：欲しい要素の単語がネガに混ざって本命が消える）を避けるため、
  問題が発生したシーンでのみONにする運用
- OFFの場合も、合成済みの最終ネガティブはUIに無効状態で表示する（ONにした際に何が入るか見えるように）
- ON/OFFの状態は `compiled.negativeApplied` に記録する（再現性のため）

## 7. コンパイル手順

1. Sceneから Situation を引き、`cast` の各スロットにCharacterを解決する
2. 5章の規則で各スロットの服装を解決する
3. 各ブロック（キャラ／服装の moss・anima）は、前後の空白を除去してから使う
4. MOSS：`mossPrompt` を**JSONとしてパース**し、各文字列値の中のプレイスホルダーを置換する
   （文字列のまま置換すると引用符でJSONが壊れうるため、この順序とする）。置換後に空白を整える。
   出力は **indent=2、ensure_ascii=False** のJSON文字列とする
5. Anima：`animaPrompt` のプレイスホルダーを文字列置換した後、
   空タグ・連続カンマのみを除去する（カンマで分割し、空白のみの要素を捨てて再結合する）。
   **重複タグは除去しない**。複数キャラの場面では、`huge breasts` のような体型タグを
   キャラごとに繰り返すことで各キャラへ行き渡らせるため、テンプレートとキャラブロックに
   書かれた通りの位置と回数を保持する
6. ネガティブを6章の規則で合成する。`applyNegative` が false なら送信ペイロードには空文字を入れる
7. 結果一式を `Scene.compiled` にスナップショットとして保存する
   （マスターデータを後で編集しても、生成済みシーンは当時の内容を再現できること）

## 8. ファイル配置

```
data/
  characters/     # 元作品別など、任意の深さのフォルダ可
  outfits/        # 任意の深さのフォルダ可
  situations/     # ストーリー → 場面 → ファイル、など任意の深さのフォルダ可
```

- フォルダ階層は整理のための棚であり、**意味はフォルダ位置ではなくファイル内容（id等）で決める**
- 参照はすべてIDで行う。フォルダの移動・改名で参照が壊れてはならない
- アプリは起動時にツリー全体を再帰スキャンし、ID→パスの索引を構築する
- ナビゲーションは階層順を基本とする：
  - 並び順はファイル名の自然順ソート（数字を数として読む）
  - ストーリー順に並べたい場合は `01_` のような番号prefixをファイル名に付ける
  - `_folder.yaml` の `order` があればそれを優先する

## 9. 検証

### 9.1 スキーマ検証（JSON Schema）

- エンティティごとにJSON Schemaを用意し、読み込み時に検証する
  （同梱の `schemas/*.schema.json` を参照）
- スキーマの割り当て：
  - `characters/` 配下 → Character用、`outfits/` 配下 → Outfit用
  - `situations/` 配下はSceneとSituationが混在するため、次の**判定規則**で区別する：
    **トップレベルに `situation` キーと `cast` キーの両方を持つファイルをScene、
    持たないファイルをSituationとする**
- YAMLファイル先頭の `# yaml-language-server: $schema=...` コメントによる
  エディタ上の検証は補助として扱う（任意の深さでは相対パスが煩雑なため）
- YAMLの書き戻し（Scene保存時など）では、コメントを保持するため **ruamel.yaml** を使う

### 9.2 意味チェック（アプリ側）

- idの重複がないこと／idとファイル名が一致すること
- 参照先（defaultOutfit、situation、cast先のキャラ、服装id）が実在すること
- プレイスホルダーとスロット宣言・cast割当の整合（5章）
- canvasが正の整数であること

## 10. 画面（UI）

v1の画面は **「シーン組み立て画面」1つだけ** とする。実装は **Python＋Gradio** を想定。
マスターデータ（Character／Outfit／Situation）の編集は、エディタで直接YAMLを編集する運用とし、
アプリ側に編集画面は作らない。

画面の内容：

- Situationを選択し、既存のSceneを開くか、新しく作る
- **選択方法はプルダウンにしない**。データはフォルダ階層が任意の深さで項目数も増えるため、
  次の2つの方法で選べるようにする：
  - UI内の**階層ツリー表示**から、フォルダを辿ってファイルを選ぶ
    （フォルダ名は `_folder.yaml` の `name` があればそれを表示し、並び順は8章の階層順とする）
  - **ファイル選択ダイアログ**を開いて、YAMLファイルを直接指定する
  - 選択中の項目は、表示名（`name`）とパスで表示する
- **Situationを読み込むと、その `slots` の数だけキャスト選択枠が動的に追加される**
  （枠にはスロット名を表示する）。各枠の内容：
  - キャラクターをツリー／ファイル選択で選ぶ
  - 服装を選ぶ。選択肢は **「未指定（継承）」「none」、およびツリー／ファイル選択で選ぶ各Outfit**
    - 「未指定（継承）」の場合は**シチュエーション側の指定する服装が適用され**、
      シチュエーション側も未指定の場合にキャラの `defaultOutfit` が適用される（5章の優先順位どおり）
    - 継承した結果として実際に使われる服装が分かるよう、枠内にその服装名を表示する
      （例：「未指定（シチュエーション指定：guilty_pink）」）
- コンパイル結果を表示する（それぞれコピーボタン付き）：
  - MOSS JSON
  - Animaプロンプト
  - ネガティブ（MOSS用・Anima用）
- ネガティブの適用ON/OFFを切り替える（既定OFF。OFFでも合成済みネガティブは表示する）
- Sceneを保存できる（`compiled` へのスナップショット保存を含む）
- 検証のエラーと警告を表示する
- データを再読み込みするボタンを付ける（YAMLを手編集した後に使う）

## 11. 受け入れテスト（例）

1. サンプルの海辺シーン（`samples/`）を読み込み、コンパイル結果が
   `samples/examples/` のMOSS JSON／Animaプロンプトと一致すること
2. 同シーンの `center` を別キャラに差し替えると、MOSS・Anima両方の出力で
   そのスロットの文章／タグだけが差し替わること
3. Situation側に服装指定がある場合、キャラの `defaultOutfit` より優先されること
4. 服装が `none` の場合、MOSSの文章に壊れた文（例：主語だけ残る）が残らず、
   Animaに空タグや連続カンマが残らないこと
5. `applyNegative: false`（既定）では送信ネガティブが空になり、
   `true` では6章の定義どおりに合成されたネガティブが入ること
6. Animaのポジティブプロンプトで、重複タグが書かれた通り保持され（キャラの人数分など）、
   空タグや連続カンマは残らないこと

## 12. 将来拡張（v1では実装しない）

- プレイの分離（シチュエーション固定を崩す場合は、プレイに `requires` とスロットを持たせる設計を別途検討）
- シーン単位の自由文の差し込み（復活させる場合は、MOSSは `summary.caption` の末尾、
  Animaはタグ列の末尾、と差し込み位置を固定してから）
- ネガティブの層ごとの個別ON/OFF
- キャストセット（三人組など、複数スロットの割当プリセット）
- シリーズ（複数Sceneの順序付きグループ）の独立エンティティ化

## 付属物

- `schemas/` … 各エンティティのJSON Schema
- `samples/data/` … サンプルデータ一式（キャラ3・服装3・シチュエーション1・シーン1）
- `samples/examples/` … サンプルシーンのコンパイル結果（MOSS JSON／Animaプロンプト／合成ネガティブの参考出力）
